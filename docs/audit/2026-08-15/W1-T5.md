### FINDINGS

#### 1. The scenario ship/hold/disable thresholds are pinned by a test that certifies them against the ceiling table CLAUDE.md retracted on 2026-08-15

- **File:line**: `Brain/tests/test_rubric_validation.py:165-171`; constants at `Brain/shared/rubric_validation.py:155-156`; the same pair duplicated at `Brain/calibration/validate_rubrics.py:102-103`.
- **What is wrong**: The test asserts `SCENARIO_MIN_ATTEMPTS == 15` and `SCENARIO_BAND == 0.05` and its docstring states they are validated — *"at these values the ceiling run's published table comes back exactly — 40 qualifying scenarios, 16 discriminating, 7 zero-control, 7 inverted."* Those two numbers were **fitted** to reproduce that table. CLAUDE.md now records the ceiling's arm B as an arm-construction artifact: arm B scored `a1_sample` rows (primary-label, the strongest exemplars) while A3 drew secondary-label rows, so `W(B)=0.090` is an inflated null. Meanwhile `validate_rubrics._items_for` (`:219-246`) deliberately **fixed** that asymmetry — *"All three arms use THE SAME A3 responses"* — so `classify_scenario` runs a symmetric comparison through a band fitted on an asymmetric one. The test locks the mismatch in and asserts it is calibrated.
- **What number it corrupts, and in WHICH DIRECTION**: `scenario_verdicts` — the harness's own headline (`validate_rubrics.py:188`, *"This is the headline output"*), printed as the SHIP/HOLD/DISABLE table by `_report_scenarios`. With a symmetric arm B the null drops (CLAUDE.md's leakage-clean `W(unrelated)` is 0.032–0.042 vs the ceiling's 0.090), so `gap = a3_w - b_w` is systematically **larger** than the population the band was fitted on. A band tuned to admit ~16 of 40 on deflated gaps admits **more** on inflated ones: **the SHIP count is inflated and the DISABLE count deflated.** The per-milestone constants at `:25-32` (`T_DISCRIMINATION`, `T_SATISFIABLE`) are pinned by the same test with the same inheritance ("Inherited from the ceiling spec's own gate") and carry the same problem.
- **Aggravating**: `_self_check` (`validate_rubrics.py:345-391`), the gate that decides whether verdicts are written to `rubrics.milestones` under `--apply` (`:794-806`), replays `artifacts/naren_ceiling.json`'s own records. So the instrument's validity proof is "does the symmetric measurement reproduce the asymmetric one's labels" — passing it is not evidence of validity. `_self_check` has **no test at all** in this batch.
- **Confidence**: certain that the thresholds are fitted to the ceiling table and that `_items_for` uses a different arm construction than the ceiling; **likely** on the direction and magnitude of the SHIP inflation (it depends on the true symmetric `b_w` per scenario, which has not been measured at scenario resolution).
- **Cheapest way to verify**: `grep -n "a1_sample\|a3_sample" Brain/calibration/score_naren_ceiling.py` to confirm arm B's source rows, then diff against `_items_for`'s `for row in sample:` loop. Then read `Brain/artifacts/naren_ceiling.json`'s `arms.B.records` and confirm they were drawn from the primary stratum.

#### 2. `classify_scenario` SHIPs on a zero control with no minimum effect size, and the only test of that path uses a case where the band would have passed anyway

- **File:line**: `Brain/shared/rubric_validation.py:179-184`; blessed by `Brain/tests/test_rubric_validation.py:173-177`.
- **What is wrong**: `control_is_zero = b_w == 0.0 and a3_w > 0`, then `elif control_is_zero or gap > band: SHIP`. `a3_w > 0` is the *only* floor — a single partial hit across 48 attempts gives `a3_w = 0.0104` and ships the rubric, bypassing the ±0.05 band entirely. `test_a_scenario_whose_control_finds_nothing_ships` exercises it with `a3=48 attempts / 13 hits` (`a3_w = 0.271`, gap +0.271), which clears the band on its own — so the test demonstrates nothing about the exception it is named for. No test probes small `a3_w` with a zero control.
- **What number it corrupts, and in WHICH DIRECTION**: the SHIP count in `_report_scenarios`, **inflated**. This is not hypothetical at the configured floor: `SCENARIO_MIN_ATTEMPTS = 15`, and CLAUDE.md's leakage-clean corpus `W(matched)` is 0.089–0.095 with the null lower still, so `b_w == 0.0` at 15–20 attempts is a routine sampling outcome rather than evidence of a working instrument. Every such scenario ships with `verdict == "ship"` while the printed annotation (`mark = verdict + " *"`) explicitly tells the reader to *"read the verdict column"*, not the asterisk.
- **Confidence**: certain about the code path and the test's non-coverage; **likely** about the frequency (the exact rate depends on per-scenario `b_w`, unmeasured).
- **Cheapest way to verify**: `python -c` is unnecessary — read `Brain/artifacts/rubric_validation.json`'s `scenario_verdicts` (if present) and count rows with `control_is_zero: true` whose `gap` is below 0.05. Any such row shipped on the exception alone.

#### 3. `scenario_verdicts` — the headline function — has no test, and the only fixture touching arm-B identity encodes the opposite convention from production

- **File:line**: `Brain/tests/test_validate_rubrics.py:25-28` (`_rec`), used for arm B at `:99, :146, :167`; untested production function at `Brain/calibration/validate_rubrics.py:187-205`.
- **What is wrong**: `scenario_verdicts` groups **both** arms by `r["scenario_key"]`, and its correctness rests entirely on the invariant stated in its docstring — *"which in BOTH arms is the scenario whose RUBRIC was scored, never the response's own."* That invariant lives one file away in `score_naren_ceiling._item` (`:410-412`: `"scenario_key": rubric_key`) and is **not asserted anywhere**. The test file's B fixtures do the opposite: `_rec(i, "other", 10, "M1", ...)` pairs `rubric_id=10` (scenario `"s"`'s rubric) with `scenario_key="other"`. In production a B record with `rubric_id=10` carries `scenario_key="s"`. The drift is invisible because `build_verdicts` keys off `(rubric_id, milestone_id)` and overwrites `scenario_key` from the A3 counter (`:175`), so nothing in the tested path reads it.
- **What number it corrupts, and in WHICH DIRECTION**: today, nothing — production is correct. The defect is that **the invariant is unprotected while the fixture teaches the wrong one.** If `_item` ever recorded the response's own scenario (which is what the fixture models), every arm-B record would be filed under the wrong scenario, each rubric's `b_w` would be computed from a different rubric's null, and every SHIP/HOLD/DISABLE verdict would be wrong — with no test failing and the report looking entirely normal. Direction would be arbitrary per scenario, i.e. the worst kind.
- **Confidence**: certain (both facts read directly from source).
- **Cheapest way to verify**: `grep -n "scenario_key" Brain/calibration/score_naren_ceiling.py` — line 412 is the only assignment; then `grep -n "scenario_verdicts" Brain/tests/` returns nothing.

#### 4. The segmenter's 4-token cutoff is claimed to be "pinned by its own test" and is not — the test survives any cutoff from 1 to 6

- **File:line**: `Brain/tests/test_layer_c_clause_pool.py:8-12` (the claim), `:22-28` (the test); real filter at `Brain/preprocessing/segmenter.py:23` (`if len(sent) < 4`).
- **What is wrong**: the test asserts only `segment_into_clauses("Sure.") == []` (2 tokens) and `len(segment_into_clauses(_ONE_SENTENCE)) == 1` (8 tokens). It never touches the boundary. Token counts of every fixture sentence: `_ONE_SENTENCE` 8; `_THREE_SENTENCES` = 7 / **6** / 7. So changing `< 4` to `< 5` or `< 6` leaves **every assertion in the file passing**. The file first breaks at `< 7`, where the 6-token middle sentence drops and `test_four_lists_stay_index_aligned` fails.

Raising the cutoff **deflates** both; the effect is silent because the suite stays green. CLAUDE.md records that this same segmenter is shared with Layer A's clause-mode pool, so a change would move the taxonomy too. The module docstring's assurance that the filter is *"pinned by its own test below rather than left as a trap for the next person"* is the specific thing that is false.
- **Confidence**: certain (token counts are mechanical; spaCy tokenises trailing `.` as its own token).
- **Cheapest way to verify**: read `Brain/preprocessing/segmenter.py:23` and count tokens in the three fixture sentences at `test_layer_c_clause_pool.py:16-19`.

#### 6. The applicability judge's null compares "ids per exchange" across rubrics with unmatched milestone counts

- **File:line**: `Brain/calibration/validate_rubrics.py:208-212` (`applicable_rate_overall`), consumed at `:772-780` and gated at `:527`; tested at `Brain/tests/test_validate_rubrics.py:182-185`.
- **What is wrong**: `applicable_rate_overall` returns `(ids returned, exchanges answered)`, and `matched_rate`/`null_rate` are that ratio — an unnormalised **count of applicable milestone ids per exchange**, bounded above by the rubric's milestone count. The null swaps in `rubrics[pkey]`, and `derange` pairs by cosine distance only (`:670`) with **no matching on milestone count**. So a partner rubric with 3 milestones cannot return more than 3 ids where the matched rubric with 8 could return 8. Taxonomy item 6: the null controls for topic and controls nothing for rubric size. The test asserts `== (2, 2)` on a hand-built dict and pins neither the normalisation nor the comparability.
- **What number it corrupts, and in WHICH DIRECTION**: `applicability_null.null_rate` and the pass/fail line `null_rate <= 0.5 * matched_rate`. If partner rubrics are on average **smaller**, `null_rate` is deflated and the judge appears to collapse for a reason that is pure arithmetic — i.e. the defect makes **passing easier**. This does not explain the recorded 1.22:1 failure (the judge failed anyway), but it means a *pass* on this check would not have been trustworthy. Secondary: `--skip-applicability`'s help text (`:591-593`) and CLAUDE.md both describe 0.147/0.120 as an *"applicable fraction"*, which this quantity is not.
- **Confidence**: likely (the size confound is certain from the code; whether partner rubrics skew small in the live corpus is unmeasured).
- **Cheapest way to verify**: read `plan[key]["milestones"]` in `Brain/artifacts/rubric_validation.json` and correlate each scenario's own milestone count with its partner's.

#### 7. A milestone whose arm-B counter is absent passes the discrimination gate for free, and the test blesses it as "a legitimate zero null"

- **What is wrong**: `_verdict` fires `NOT_DISCRIMINATING` on `a3_w > 0 and b_w >= T_DISCRIMINATION * a3_w`. It never consults `b["attempts"]`, so **"the null was measured and came back empty" and "the null was never measured" are indistinguishable** — both give `b_w = 0.0`, and discrimination is the *first* gate. `main()` guards the whole-rubric case by aborting unless the pairing is a true derangement (`:674-681`, with a comment naming exactly this failure), but per-milestone B counters can still be empty when a B batch raises `GemmaError` (`_score_arm` `continue`s on the whole batch). The per-milestone resolution is already written off, so consequence today is limited to any future re-read of `rubric_validation.json`.
- **Confidence**: certain about the code path; **speculative** about how many milestones are actually affected in the stored artifact.

#### 8. `test_order_within_a_scenario_is_preserved` is named and documented for a property it cannot protect

- **File:line**: `Brain/tests/test_layer_c_describe.py:44-51`.
- **What is wrong**: the docstring claims *"milestone_id is the array POSITION. If grouping reorders a scenario's items, every id downstream shifts and existing milestone_performance rows silently repoint at a different criterion."* That is false. `group_describe_items_by_scenario` feeds only the prompt; the stored `order` is re-derived independently by `_finish_rubric` (`v2/layer_c.py:613`, `enumerate(ordered)`), and the description lookup is by content id `f"{scenario_key}::{cluster_id}"` (`:614`), not by position. - **Confidence**: certain.

#### 9. Minor: the discrimination-boundary test never exercises the quantization blind spot it exists for, and says it does

### CLEAN

Stated so the next person does not re-check these.

- **Taxonomy 3 (base mismatch), the positional-`milestone_id` convention.** I traced it end to end and found **no live instance**. `milestone_scoring.milestone_ids` (`:69-87`) is the single definition, `score_milestones_batch` zips it over the **full** unfiltered list (`:245-254`) so skipping never renumbers, `_write_verdicts` rebuilds by `enumerate(ids)` position (`validate_rubrics.py:319`), and `_finish_rubric` writes `order = order_idx + 1` over the same list it stores. `test_the_same_milestone_id_stays_separate_across_rubrics` (`test_validate_rubrics.py:86-93`) correctly pins that `"M1"` is a different criterion per rubric. The only conflation is documentary, in finding 8.
- **`shared/coverage_areas.py` parse and roll-up logic.** I hand-checked all 14 parsing/evidence assertions against the implementation and every one is arithmetically correct: `support_calls` really is `max` (`:106`) and `support_clauses` really is `sum` (`:107`); `normalize_verdict` really defaults to `NOT_COVERED` and never to `NOT_CALLED_FOR` (`:150`), which is the one direction that could not be detected downstream; `score`'s two denominators are `total` and `total - not_called_for` (`:169-176`) and both are reported, matching the profile-rebuild spec's symmetric-filtering rule. `wide_merge` uses `>=` against 4, and `test_a_two_move_area_is_not_flagged_as_a_merge` pins the non-firing side.
- **Taxonomy 4 (name that never matches).** Every string literal in this batch's tests exists in the module it names: `rv.VALIDATED/CONTINGENT/NOT_SATISFIABLE/NOT_DISCRIMINATING/INSUFFICIENT_EVIDENCE`, `rv.SCENARIO_SHIP/HOLD/DISABLE/INSUFFICIENT`, `ca.COVERED/PARTLY_COVERED/NOT_COVERED/NOT_CALLED_FOR`, and the verdict strings `"full_hit"/"partial_hit"/"miss"` used by `vr.tally` all match `milestone_scoring`'s vocabulary. Report keys (`unknown_clusters`, `uncovered_clusters`, `double_claimed_clusters`, `empty_areas`, `malformed_areas`, `unanswered`, `unknown_ids`) all exist in the returned dicts.
- **Taxonomy 5 (a metric that cannot fail) in `_self_check`.** `passes` requires `ok_total > 0` **and** `bad_total > 0` (`validate_rubrics.py:389-390`), so an empty ceiling artifact or an out-of-scope zero-control set fails closed rather than passing vacuously. The instrument's *baseline* is the problem (finding 1), not its degenerate case.
- **The three-state applicability parse.** `rv.parse_applicability` genuinely distinguishes unanswered (`None`), answered-empty (`set()`) and answered-with-ids, and `applicability_counters` excludes `None` from **both** counters (`:142-148`). `test_an_unanswered_exchange_counts_in_neither_set` and `test_an_empty_applicable_list_means_nothing_applied` pin both sides. This is the one place in the batch where the asymmetric-denominator trap was correctly avoided and correctly tested.
- **Fixture shape drift, `_real_milestone`.** `test_rubric_validation.py:467-477` matches the JSONB `_finish_rubric` actually stores (`v2/layer_c.py:615-633`) field-for-field, with `criteria_rewritten`/`not_coachable_flag` added — the two flags later repair passes wrote. The only field in production absent from the fixture is `precondition` (`:624`), added by the situated path; `with_validation` copies unknown fields wholesale (`dict(milestone)`), so its absence does not weaken the preservation test.
- **Scope note, not a defect**: `shared/coverage_areas.py`'s docstring says *"Selected by layer_c.describe_mode == 'coverage'"*, but `run_layer_c_v2` branches only on `"situated"` (`v2/layer_c.py:802`) and `shared/tuning.py:63` declares `describe_mode: str` with no enum validation — so setting `coverage` in `tuning.yaml` would silently run legacy. `tests/test_tuning.py:110` (outside this batch) asserts the live value is in `("legacy", "situated")`, which would catch it loudly. The coverage path is reachable only from `calibration/trial_layer_c_arms.py`. Flagging so nobody reads the module docstring as a production selector; not counted as a finding since the live config is `legacy` and the guard exists.
