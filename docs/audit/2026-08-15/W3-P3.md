### FINDINGS

#### 1. `extract_pairs` silently discards every CLIENT turn in a consecutive client block except the last — and discards the WHOLE block if the last turn is filler

- **File:line**: `Brain/v1/layer_b.py:51-70` (the `else: break` at :59-60 and `i = j if response_parts else i + 1` at :70)
- **What is wrong**: The inner loop walks forward from a client turn and **breaks on the first
  turn that is neither NAREN nor JOVEO_OTHER** — i.e. on the next CLIENT turn. So for
  `[C1, C2, NAREN]`, C1 breaks immediately with `response_parts == []`, is dropped, and only
  `(C2 -> NAREN)` becomes a pair. C1's text never enters `kb_pairs` as a trigger and never as a
  response. Worse, if the *last* turn of the block fails `_is_substantive` (`[C1(substantive),
  C2("Yeah."), NAREN(substantive)]`), C1 breaks out, C2 is filtered, and the block yields **zero
  pairs** — both the real client question and Naren's substantive answer are lost. Nothing counts
  any of this.
- **What number it corrupts, and in WHICH DIRECTION**: Deflates `kb_pairs` (the input population
  for Layer B, Layer C's clause pool and every rubric), and — more damagingly — **systematically
  biases `trigger_text` toward the last fragment of each client speech block**, which is the
  fragment most likely to be a trailing "so yeah, anyway". Layer B's sink decision is made on
  `trigger_text` alone, so this inflates the sink-filing rate. This is the same defect class as
  the recorded Layer D `turns_until_next_client` DEFECT 1 (measured there: **2,449 of 5,731 client
  turns — 43% — are immediately followed by another CLIENT turn**), one layer earlier and, as far
  as I can find, never diagnosed for Layer B. If the Naren corpus has a comparable rate, ~40% of
  client turns cannot become a trigger by construction, which is a plausible mechanical cause of
  the 39.7–45.8% sink absorption that the whole sink-rescue effort (eight signals, four design
  docs) was searching for a *scoring* explanation for.
- **Confidence**: certain for the mechanism (traced line by line); likely for the magnitude, which
  is inferred from the measured CSM-corpus rate rather than measured on `recordings/`.
- **Cheapest way to verify**: free, no DB — parse the 416 transcripts with
  `preprocessing.transcript_parser.parse_transcript` and count client turns whose next turn is
  also CLIENT; compare to `len(extract_pairs(turns, 0))` per file.

#### 2. Layer C's "relevance filter" is a fixed 60% quota, not a filter — it can never reject anything and never fails

- **File:line**: `Brain/v2/layer_c.py:108-109`
- **What is wrong**: `cutoff = np.percentile(relevance, percentile)` then `keep = relevance >= cutoff`.
  A percentile of the population being filtered always keeps exactly `100 - percentile` percent of
  it (ties aside). At the calibrated `milestone_relevance_percentile: 40` this drops the bottom 40%
  of clauses from **every** scenario regardless of whether any clause is off-topic, and keeps 60%
  even if every clause is off-topic. The docstring frames it as "drop response clauses that are not
  about the scenario", and the printed line reads
  `Relevance filter (>40th pct): 2315 -> 1389 clause(s)` as though the ratio were informative — it
  is 0.60 by construction for every scenario in every run.
- **What number it corrupts, and in WHICH DIRECTION**: Taxonomy item 5. It mechanically explains
  the recorded open finding "Layer C's relevance filter barely discriminates by topic —
  deliberately wrong placebo clauses survived the p40 cut at 53.9–57.2% vs 57.7–63.0% for real
  content": a quota cannot separate them, and the ~6-point gap is only the residual ordering
  effect. Consequence: for a clean scenario it **deflates** the milestone clause pool by 40% for
  nothing; for a contaminated one it **cannot** remove the contamination. It also invalidates any
  reading of the percentile sweep as a *quality* knob — the sweep was measuring pool size.
- **Confidence**: certain.
- **Cheapest way to verify**: read the two lines; or grep the run logs for
  `Relevance filter` and confirm every `N -> M` line has `M/N ≈ 0.60`
  (`grep "Relevance filter" Brain/logs/*.log`).

#### 3. Every "sample" fed to a Gemma prompt in Layer C is an alphabetical head slice, while the evidence count reported alongside it covers the whole population

- **File:line**: `Brain/v2/layer_c.py:635` (`responses[:_MAX_RUBRIC_RESPONSES]`), `:793`
  (`cluster["clauses"][:5]`), `:728` (`cand["clauses"][:5]`), `:796` (`pair_ids` order);
  ordering comes from `shared/storage.py:306` `ORDER BY p.pair_id`
- **What is wrong**: `pair_id` is a SERIAL assigned during Layer B, which processes calls in
  `sorted(rec_path.glob("*.txt"))` order (`v2/pipeline.py:13`) — i.e. **alphabetical by
  filename**. So `responses[:12]` is "the 12 responses from the alphabetically earliest calls",
  and `clauses[:5]` is "the 5 clauses from the earliest calls in this cluster". This is taxonomy
  item 13, the exact `--limit N` failure the calibration section already documents, sitting in
  production code. `_finish_rubric` then stores `support_clauses: len(cluster["clauses"])` (the
  full count, up to 337 in a measured case) next to a description written from 5 of them.
- **What number it corrupts, and in WHICH DIRECTION**: Every rubric's `anti_patterns` and
  `soft_skill_rubric` (generated from `sample_responses` with `n_instances=len(sample_responses)`,
  so the prompt is truthfully told 12 but the *selection* is biased), and every milestone `label`
  / `description` / `detection_hint`. Direction is a bias, not an inflation: criteria are written
  from the earliest-named accounts. Given the separately-measured finding that clusters are often
  account-bound (`happy dance`, `uber.com` 19.6% of turns), an alphabetical head slice is close to
  a worst case — it concentrates on whichever accounts sort first.
- **Confidence**: certain for the mechanism (`ORDER BY p.pair_id` + `sorted(glob)`); the size of
  the resulting bias is unmeasured.
- **Cheapest way to verify**: `SELECT call_filename FROM ... ORDER BY pair_id LIMIT 12` for two
  large scenarios and check whether the 12 come from ≤3 distinct accounts.

#### 4. `topk_pick` and `flat_pick` apply the cap at different points, so Layer D and every matching harness measure a MORE PERMISSIVE rule than production Layer B

- **File:line**: `Brain/shared/relative_match.py:81-89` vs `:108-116`, and production
  `Brain/v1/layer_b.py:140-143`
- **What is wrong**: `flat_pick` (and the byte-identical inline rule in production
  `assign_scenarios`) takes `order[:cap]` **first** and then discards sinks — so a sink sitting at
  rank 2 consumes one of the 3 slots and the pair ends with 2 matches. `topk_pick` builds the
  non-sink candidate list **first** and then takes `candidates[:cap]` — so it always returns up to
  3 real scenarios. With 76 of 161 scenarios flagged as sinks, a sink inside the top 3 ranks is
  common, so the two rules genuinely differ. `topk_pick` is what Layer D uses, what
  `assign_scenarios_two_stage` uses for **all three** strategies (including the `fallback`
  strategy's supposedly-flat branch at `v1/layer_b.py:231`), and what
  `calibration/compare_matching_subset.py` imports as `_topk_pick`.
- **What number it corrupts, and in WHICH DIRECTION**: (a) Taxonomy item 1 — the two-stage-vs-flat
  comparison (86.6% subset / 61.3–77.0% full corpus recall-proxy) has a **second uncontrolled
  variable**: the arms differ in cap semantics as well as in two-stage-ness, and the direction
  favours the two-stage arms (more surviving matches → higher Jaccard/recall-proxy). (b) Any
  "match width" figure derived from `topk_pick` **inflates** the multi-label rate relative to what
  production writes into `scenario_keys[]`. The module docstring says "moved verbatim", which reads
  as a guarantee that they are the same rule; they are not.
- **Confidence**: certain that the two functions differ; likely that it moved the two-stage
  numbers (the sign is clear, the size is unmeasured).
- **Cheapest way to verify**: zero cost — construct one `sims` vector where rank 2 is a sink and
  call both functions with `cap=3`; `flat_pick` returns 2 keys, `topk_pick` returns 3.

#### 5. `_sequence_milestones`'s substring test can essentially never match, and nothing counts the misses

- **File:line**: `Brain/v2/layer_c.py:370-373`
- **What is wrong**: Verified as recorded. A milestone is reclassified `conditional` only if
  `position_variance > 0.3` AND `len(responses) >= 3` AND
  `item["label"].lower() in " ".join(m["clauses"][:2]).lower()` — a raw substring test of a Gemma-
  authored 2-4 word label against the concatenation of two verbatim transcript clauses. Gemma is
  asked to *name* the move, so the label is a paraphrase; an exact substring hit requires it to
  quote. Every non-match falls through silently and `sequencing_map.get(cluster_id, "fixed")`
  (`:625`) writes `"fixed"`. Two further defects in the same three lines: the inner loop has no
  `break`, so one label can claim multiple clusters; and `item["label"]` / `hv_result.get(...)` are
  unguarded (a bracket access and a `.get` on a possibly-list response).
- **What number it corrupts, and in WHICH DIRECTION**: `milestones[].sequencing_type` is pinned at
  `"fixed"` — this IS the recorded "234 of 235 labelled `fixed`, conditional fires 0 of 226". The
  field reads as a measured property of the data ("this move has no ordering variance") when it is
  really "the substring test failed". Deflates the conditional count to ~0.
- **Confidence**: certain for the mechanism; the 0-of-226 rate is already recorded independently.
- **Cheapest way to verify**: `SELECT jsonb_array_elements(milestones)->>'sequencing_type', count(*)
  FROM rubrics GROUP BY 1` — a single-valued result confirms it.

#### 6. In the PRODUCTION describe path, a milestone the model failed to return is stored with an empty description and no warning

- **File:line**: `Brain/v2/layer_c.py:590-593` (legacy batch) vs `:549-556` (situated batch), consumed
  at `:613-619`
- **What is wrong**: `_describe_situated` diffs returned ids against the batch and prints
  `"describe returned N/M ... left undescribed"`. `_describe_milestones_batch` — the path
  production runs, since `tuning.yaml` ships `describe_mode: legacy` — does no such check.
  `_finish_rubric` then does `desc.get("label", f"Milestone {n}")` and
  `desc.get("description", "")`, so a missing id becomes a stored milestone titled
  "Milestone 3" with an **empty** `description` and `detection_hint`, carrying full
  `support_calls`/`support_clauses` evidence as if it were real.
- **What number it corrupts, and in WHICH DIRECTION**: An empty-criterion milestone is unhittable
  by construction, so it enters `milestone_performance.attempts` and contributes only misses —
  **deflating the weighted hit rate** (the 0.068–0.080 figure) with no trace. It also inflates the
  milestone count. Nothing anywhere reports how many milestones ended undescribed, so the ceiling
  measurement cannot distinguish "Naren failed this criterion" from "this criterion is the empty
  string".
- **Confidence**: certain for the code path; the number of affected milestones is unmeasured.
- **Cheapest way to verify**: free, one query —
  `SELECT count(*) FROM rubrics, jsonb_array_elements(milestones) m WHERE m->>'description' = ''
   OR m->>'label' LIKE 'Milestone %'`.

#### 8. `scenarios.support_clauses` and `scenarios.call_coverage` hold two different units / two different denominators depending on which code path wrote the row

- **File:line**: `Brain/v2/layer_a.py:457` + `:554-555` + `:420` vs
  `Brain/response_taxonomy_auto_pass.py:201` + `:293-294`
- **What is wrong**: Layer A sets `total_calls = len(set(call_ids))` — calls contributing at least
  one CLIENT item, **400** on the live corpus, not 416 — and writes `support_clauses =
  stats.n_items`, a count of pool ITEMS (clauses/turns). The auto-pass computes
  `SELECT COUNT(*) FROM calls` (**416**) for its denominator and writes `support_clauses = n_pairs`,
  a count of **kb_pairs**. Same two columns, two denominators and two units.
- **What number it corrupts, and in WHICH DIRECTION**: A graduated scenario's `call_coverage` is
  **deflated ~4%** relative to a Layer-A scenario's, and its `support_clauses` is on a completely
  different scale (a pair ≈ several clauses), so any ranking, filter or threshold applied across
  the `scenarios` table compares incomparable numbers. Note the production Layer A path is
  internally self-consistent and 400 is the defensible denominator — the recorded
  "`call_coverage` computed against 416" applies to the calibration trials, **not** to
  `v2/layer_a.py`. That recorded fact should be narrowed.
- **Confidence**: certain.
- **Cheapest way to verify**: `SELECT triage_verdict, min(call_coverage), max(call_coverage),
  avg(support_clauses) FROM scenarios GROUP BY 1` — the
  `graduated_from_sink_pool_auto_pass` rows will sit on a different scale.

#### 9. `min_cluster_size_ceiling` freezes Layer C's granularity exactly the way `fit_topic_model`'s hardcoded 50 freezes Layer A's — and it demonstrably binds

- **File:line**: `Brain/shared/cluster_evidence.py:193-197`, called from `Brain/v2/layer_c.py:232-235`;
  the Layer A sibling is `Brain/v2/layer_a.py:96-98`
- **What is wrong**: `int(max(floor, min(ceiling, round(fraction * pool_size))))` with
  `min_cluster_size_fraction: 0.02` / `min_cluster_size_ceiling: 25`. For any clause pool
  ≥ 1,250 the `min(ceiling, …)` term wins and `min_cluster_size` is a **hardcoded count of 25**,
  so a 3,000-clause scenario clusters at a 0.83% bar while a 600-clause one clusters at 2%. The
  recorded sink-pool diagnostic already caught this firing (`0.02 × 3730 = 74.6, clamped to 25`)
  and attributed the resulting 47.3% HDBSCAN noise to "coarse clustering" — the ceiling is why.
  Same taxonomy item 15 as the audited `max(3, min(n // 10, 50))`, and the same violation of this
  project's own "a threshold must never be a count" rule.
- **What number it corrupts, and in WHICH DIRECTION**: **Inflates** the milestone-candidate count
  for large scenarios relative to small ones, so per-scenario milestone counts are not comparable
  across the corpus and the total milestone count (the 385/398/404 band used as the run-health
  indicator) is partly a function of pool size rather than of content.
- **Confidence**: certain for the mechanism; the recorded clamp measurement confirms it binds.
- **Cheapest way to verify**: free — print `round(0.02 * len(all_clauses))` next to the returned
  `min_cluster_size` at `v2/layer_c.py:236` for the ten largest scenarios, or read the
  `sink_pool_clusters.json` artifact which already records `_mcs`.

#### 11. The auto-pass consensus counter cannot advance when the corpus is unchanged, because the guard is keyed on `run_id`

- **File:line**: `Brain/response_taxonomy_auto_pass.py:128-129`, consumed at `:393`
- **What is wrong**: `if matched_row["last_seen_run_id"] == run_id: return` is an idempotency
  guard, but `run_id` is a **sha1 of the sorted transcript stems** — identical across every re-run
  of the same corpus. So the second and third pipeline runs over an unchanged `recordings/` match
  the existing tracking row, hit the guard, and never increment `consensus_count`; the candidate
  then fails `consensus_count < response_taxonomy_consensus_runs` at `:393` and `continue`s with no
  log line. The consensus mechanism only advances when the transcript set changes, which is the
  opposite of the stated intent ("must reappear across 3 consecutive runs" as a defence against
  UMAP/HDBSCAN instability — instability that is exercised by re-clustering the *same* corpus).
- **What number it corrupts, and in WHICH DIRECTION**: **Deflates the graduation count to zero** on
  a stable corpus (fail-safe direction, so this is a stalled feature rather than a wrong number),
  and it means the 2026-08-08 result of "4 scenarios graduated after 3 manual invocations" was only
  reachable because those invocations supplied differing `run_id`s — i.e. the consensus that was
  actually satisfied is not the one the design describes. Taxonomy item 12: the key does not
  include what makes the record meaningful (the clustering outcome), and it includes something that
  makes repetition impossible (the corpus hash).
- **Confidence**: certain for the code path; likely for the interpretation of the recorded run
  (I did not inspect how those three invocations were launched).
- **Cheapest way to verify**: `SELECT candidate_id, consensus_count, first_seen_run_id,
  last_seen_run_id FROM response_taxonomy_candidates` — equal first/last run ids with
  `consensus_count = 1` across several runs confirms it.

#### 12. `_resolve_primary_topic_key` borrows a cosine threshold across two different, never-measured bands
