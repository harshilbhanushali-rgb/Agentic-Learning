### FINDINGS

#### 1. `flat_pick` and `topk_pick` apply `cap` to DIFFERENT populations — sinks silently consume match slots

- **File:line**: `Brain/shared/relative_match.py:89` vs `:114` (and the production copy at
  `Brain/v1/layer_b.py:141`)
- **What is wrong**: `topk_pick` builds `candidates` = non-sink indices in descending similarity
  order and then slices `candidates[:cap]`. `flat_pick` slices the RAW ranking `order[:cap]` and
  filters sinks *afterwards*. So in `flat_pick` a sink sitting between the best match and a
  qualifying real match consumes one of the `cap` slots and evicts the real match, while
  `topk_pick` keeps it.

  Concrete divergence with `cap=3, margin=0.95` (cutoff = 0.855):
  `sims = [realA 0.90, sink 0.89, sink 0.88, realB 0.87]`
  → `flat_pick` returns `[realA]`; `topk_pick` returns `[realA, realB]`.

  This is not a hypothetical population: 76 of 161 live scenarios (47%) are sinks, so sinks
  populate the top of the ranking routinely. The module docstring presents both functions as "the
  relative top-K matching rule, in one place", and `topk_pick`'s own docstring says "keep entries
  within `margin` of the best among the … non-sink candidates, capped at `cap`" — which is the rule
  `flat_pick` does **not** implement.

  The guard that should have caught this is vacuous:
  `tests/test_relative_match.py:149 test_flat_pick_matches_topk_pick_when_the_best_is_not_a_sink`
  asserts the two are equal but passes `is_sink = [False, False, False]` — a case in which they
  cannot differ by construction.

- **What number it corrupts, and in WHICH DIRECTION**:
  - **DEFLATES** the width of `kb_pairs.scenario_keys[]` in production. The measured production
    width "63% one / 19% two / 18% three" is partly an artifact of sinks eating cap slots, not
    purely of the relative margin. CLAUDE.md attributes the whole 63/19/18-vs-47/25/27 gap to the
    sink *short-circuit* (pairs whose BEST match is a sink); this is a second, undocumented
    narrowing that also hits pairs whose best match is a real scenario.
  - **DEFLATES** the candidate pool of `get_responses_for_scenario_multilabel` (the one consumer
    of `scenario_keys[]`), i.e. Layer D's benchmark-reference pool — the "2,904 → 5,463 responses"
    gain is smaller than the rule alone would give.
  - **DEFLATES** the flat-vs-two-stage agreement/Jaccard reported by
    `calibration/compare_matching_subset.py`, which scores `_topk_pick` output (line 137) against
    `r["flat_keys"]` read from a DB written by the inline `flat_pick` rule. The two arms differ in
    cap semantics as well as in the two-stage restriction — so part of the measured disagreement
    (strict 79.6%, fallback 86.6%, and the full-corpus 61.3/71.4% recall-proxy) is this defect,
    not the treatment. This is taxonomy item 1 (asymmetric arms) with the asymmetry living in the
    shared helper rather than in the harness.
- **Confidence**: certain (on the code divergence and the worked example); **likely** on the
  magnitude of the width effect, which is unmeasured.
- **Cheapest way to verify**: add a sink between the ranks in the existing equivalence test —
  `flat_pick(np.array([0.90,0.89,0.88,0.87]), keys, [False,True,True,False], 3, 0.95)` vs
  `topk_pick(...)` with the same args. No DB, no network. To size the production impact:
  `SELECT array_length(scenario_keys,1), count(*) FROM kb_pairs GROUP BY 1;` and compare against
  a re-run of the margin rule with `topk_pick` on the same stored vectors.

#### 2. `review_flag_threshold` flags a fixed fraction of milestone candidates by construction — it cannot report "no contamination"

- **File:line**: `Brain/shared/cluster_evidence.py:171`, consumed at `Brain/v2/layer_c.py:713-728`
- **What is wrong**: the threshold is the `milestone_sink_similarity_percentile` (95, per
  `tuning.yaml:468`) of *the run's own* candidate population, and candidates are flagged with
  `sink_similarity >= threshold`. That is a rank statistic over the set being judged, so ~5% of
  candidates are flagged **always** — in a corpus with zero backchannel contamination and in a
  corpus that is half backchannel alike. The docstring calls this "self-scaling … consistent with
  every other threshold in this file", but the other thresholds in the file
  (`required_call_support`, `required_milestone_support`, `passes_reconciliation_gate`) are
  absolute properties of the data; this one is not. It is taxonomy item 5: the metric cannot fail,
  and its degenerate value is a constant.
- **What number it corrupts, and in WHICH DIRECTION**: the count of milestone clusters sent to
  `_judge_flagged_milestones` and therefore the count dropped as `mechanics`. It is **capped at
  ~5% of candidates regardless of the true contamination rate** (so if contamination is higher,
  milestone counts are **INFLATED** with junk that is never examined) and **floored at ~5%** (so on
  a clean run ~5% of legitimate milestone clusters are still put in front of a judge that can drop
  them, **DEFLATING** the milestone count). CLAUDE.md's "only 21 [of ~400] ever flagged for the
  batch judge" is arithmetic, not evidence that contamination was low — that sentence should not
  be cited as a quality result.
- **Confidence**: certain (the mechanism); the direction of the net effect depends on the unknown
  true contamination rate, which is the point.
- **Cheapest way to verify**: read `Brain/v2/layer_c.py:705-728` — `all_sims` is the full candidate
  population and `threshold` is its p95, so `len(flagged) ≈ 0.05 * len(all_sims)` identically. Any
  Layer C run log line `"Review-flag threshold (p95 over N milestone candidate(s))"` followed by
  `"M milestone candidate(s) flagged"` will show `M/N ≈ 0.05` in every run.

#### 3. `milestone_min_cluster_size`'s ceiling makes the "scales with the pool" formula a hardcoded 25 for every large scenario

- **File:line**: `Brain/shared/cluster_evidence.py:193-197`; values at `tuning.yaml:435-437`
  (`fraction 0.02, floor 3, ceiling 25`)
- **What is wrong**: `int(max(floor, min(ceiling, round(fraction * pool_size))))` is a genuine
  fraction only while `0.02 * pool_size < 25`, i.e. below **1,250 clauses**. Above that it is the
  literal 25 forever. This is the exact shape taxonomy item 15 names
  (`min_cluster_size = max(3, min(n//10, 50))`). Layer C's per-scenario pools exceed 1,250 for the
  large scenarios — CLAUDE.md records clause pools of 2,315 and 3,239 for
  `client_requests_operational_visualization` alone, and `diagnose_sink_pool` recorded
  `0.02 × 3730 = 74.6` clamped to 25.
- **What number it corrupts, and in WHICH DIRECTION**: the milestone-candidate count per scenario,
  and asymmetrically. A small scenario is clustered at 2% of its pool; a large one at a fixed 25,
  which is a *proportionally looser* bar — so large scenarios produce **MORE** milestone candidates
  than the stated rule implies (**INFLATES** their candidate count), while small ones are held to
  the true fraction. That directly contradicts the sibling docstring at
  `cluster_evidence.py:181-190` ("a 200-call scenario cannot accumulate milestones merely by being
  large"). It also means the total milestone count (the 385/398/404 baseline everything is
  compared against) is not invariant to corpus growth in the way the formula suggests: adding
  transcripts grows pools past the ceiling and freezes granularity.
- **Confidence**: certain on the arithmetic; **likely** on the size of the effect (the downstream
  `required_milestone_support` gate absorbs some of it, and it has not been swept — `tuning.yaml`
  says these were "swept … and shown NOT to matter", but that sweep predates the pools growing).
- **Cheapest way to verify**: no run needed —
  `python -c "from shared.cluster_evidence import milestone_min_cluster_size as f; print([f(n,0.02,3,25) for n in (500,1000,1250,2000,3239)])"` → `[10, 20, 25, 25, 25]`. To see whether it
  binds in practice, grep any Layer C log for the per-scenario clause count printed at
  `v2/layer_c.py:223` and check how many exceed 1,250.

#### 4. Production Layer B does not call the shared rule it was extracted into

- **File:line**: `Brain/v1/layer_b.py:127-144` vs `Brain/shared/relative_match.py:93-117`
- **What is wrong**: `relative_match.flat_pick` is documented as "moved verbatim from
  `v1/layer_b._flat_pick`", and the module docstring says the rule lives "in one place". But
  `assign_scenarios` — the only Layer B path the production pipeline calls
  (`v2/pipeline.py:46`) — still contains its own inline copy of the sink short-circuit and the
  `order[:cap]` margin loop. It imports `is_sink_flags` from `shared` but not `flat_pick`. Only
  `assign_scenarios_with_sink_rescue` (not production) calls `_flat_pick`.
- **What number it corrupts, and in WHICH DIRECTION**: nothing today — the two copies are
  currently byte-equivalent, so this moves no number as it stands. It is reported because it is the
  mechanism by which finding #1 would be "fixed" in `shared/relative_match.py`, verified by
  `tests/test_relative_match.py`, and leave **production unchanged** — while every calibration
  harness that imports the shared function would then be measuring a rule production does not run.
  That is the confounded-arm failure this repo has already hit ("a Layer B sweep that
  reimplemented the sink short-circuit once disagreed with production by 99.7% vs 14%").
- **Confidence**: certain (code fact); the numeric consequence is conditional and prospective —
  flag it, do not count it as a live defect.
- **Cheapest way to verify**: `grep -n "flat_pick" Brain/v1/layer_b.py` — no hit inside
  `assign_scenarios` (lines 60-146).

#### 5. A scenario vector and a primary-topic vector are compared using a threshold calibrated on neither band

- **File:line**: `Brain/shared/scenario_vectors.py:35` + `:45`, consumed at
  `Brain/response_taxonomy_auto_pass.py:177-180` and `calibration/graduate_sink_topics.py:125-128`
- **What is wrong**: both graduation paths embed the new scenario with `scenario_vec()`
  (`business_description + keyphrases`) and the existing parents with `build_primary_topic_vecs()`
  (`description + keyphrases`), then decide the FK with
  `topic_grouping.match_existing_primary_topic(..., merge_cosine_threshold)`. The prefix is right —
  both are `embed_document`, so this is *not* the query/document cache-key bug — but
  `merge_cosine_threshold` (0.85) was calibrated on **cluster-centroid vs cluster-centroid of
  clause embeddings**, a third population, and validated by reading merge groups at that level. The
  scenario-description-vs-primary-topic-description cosine band has never been measured in this
  repo. This repo's own rule is "Never borrow a floor between the two [bands]" — the
  trigger-vs-scenario, response-vs-scenario and trigger-vs-trigger bands are all separately
  measured precisely because they differ (p50 0.550 / 0.635 / 0.689).
- **What number it corrupts, and in WHICH DIRECTION**: `scenarios.primary_topic_key` for every
  auto-pass-graduated scenario. If the description-vs-description band sits higher than the
  centroid band (the pattern everywhere else in this codebase — richer, longer text scores higher),
  0.85 is **too permissive** and graduated scenarios are **over-attached** to a near-but-wrong
  parent; if lower, they are orphaned to `None`, which is the exact bug
  `match_existing_primary_topic` was written to fix. Affects the 4 scenarios graduated in the
  2026-08-08 run and every future one. It does not touch Layer B/C/D matching.
- **Confidence**: likely (the threshold-transfer is certain; whether it currently mis-assigns is
  unmeasured — mark this as unverified, not as a demonstrated mis-assignment).
- **Cheapest way to verify**: free and offline against the live DB read-only — embed the 161
  `scenario_text()` strings and the 80 `primary_topic_text()` strings (warm cache, no API) and
  print the percentiles of each scenario's best-match cosine. If p10 sits above 0.85, the
  threshold admits everything.

#### 6. `insert_kb_pair` silently discards a conflicting pair and reports it as stored

- **File:line**: `Brain/shared/storage.py:176-203`
- **What is wrong**: `ON CONFLICT (call_id, turn_index) DO NOTHING` followed by a re-SELECT of the
  existing `pair_id`. On conflict the function returns the **pre-existing** row's id and the newly
  computed `scenario_key` / `scenario_keys` / `trigger_text` / `response_text` are thrown away.
  There is no counter, no return-value difference and no log line distinguishing "inserted" from
  "already there" — taxonomy items 9 and 10 in one function.
- **What number it corrupts, and in WHICH DIRECTION**: `v2/pipeline.py:51` prints
  `"Stored {len(pair_ids)} pair(s)"`, which counts silent no-ops as stores — **INFLATES** the
  reported store count to exactly the extracted-pair count no matter how many writes actually
  landed. More consequentially, a Layer B re-assignment run over a DB whose `checkpoints.db` was
  cleared but whose `kb_pairs` was not (the precise state CLAUDE.md warns about) will report full
  success while leaving every `scenario_key` at its OLD value — so a downstream Layer C/D
  measurement would be attributed to the new taxonomy while running on the old assignments.
- **Confidence**: certain on the code; **likely** on it having occurred (it requires the
  checkpoints-cleared-but-data-kept state).
- **Cheapest way to verify**: read the function — `row is None` after `RETURNING` is the conflict
  branch and it is indistinguishable to the caller. A one-line fix would be returning
  `(pair_id, inserted: bool)`; do not apply it, just note the branch is unobservable.

- `get_milestone_gap_profile` — `WHERE mp.csm_id = %s AND mp.attempts >= %s` plus
  `JOIN rubrics ON rubric_id`. The join cannot drop rows: `milestone_performance.rubric_id` is a
  FK to `rubrics(rubric_id)` (`db/schema.sql:199`). `min_attempts` defaults to 1, so nothing is
  excluded unless a caller asks. Correct.
- `count_scenarios_without_status` / `get_rubric_status_report` — both count **every** row in
  `scenarios`, with no run scoping, because there is no `run_id` column (documented). `_reconcile`
  prints `len(scenario_map)` beside them, so on an uncleared DB the two numbers describe different
  populations. This is the already-documented "you cannot keep two runs in the DB at once"
  constraint, not a new defect.
- `upsert_scenario`'s `ON CONFLICT DO UPDATE` deliberately does **not** touch `rubric_status`,
  which is correct for the resume path (Layer C owns that column) and is re-set on any genuine
  re-run because `run_id` changes and the Layer C checkpoint therefore misses.
- The documented accumulation hazards are all confirmed present and are working as designed, not
  as bugs: `upsert_milestone_performance:439` does `attempts = attempts + 1`;
  `insert_gap_event` has only a SERIAL PK; `upsert_rubric`'s `ON CONFLICT (scenario_id)` keeps
  `rubric_id` stable while replacing `milestones`. All three are already documented in
  `db/schema.sql:186-190` and CLAUDE.md, and all three are mitigated by the mandatory
  `ops/clear_ego_trap_data.py`. I found no *additional* accumulation path.

**`cluster_evidence.merge_by_similarity` — the distance/similarity conversion is correct.**
`distance_threshold = 1.0 - threshold` with `metric="cosine"`, `linkage="average"`. Average-linkage
over cosine *distances* equals `1 −` the average of the corresponding cosine *similarities*, so
`mean_distance < 1 − t` is exactly `mean_similarity > t`, matching the docstring. Degenerate inputs
are handled (`len 0 → []`, `len 1 → [[0]]`) and the result is deterministic (groups sorted).
`support_stats` raises on non-parallel inputs and on `total_calls <= 0` rather than dividing
silently. `nearest_sink_index` and `review_flag_threshold` both raise on an empty population
instead of returning a sentinel.
