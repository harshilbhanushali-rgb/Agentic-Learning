### FINDINGS

#### 1. The ONLY test of `classify_response_outcome(...) == "none"` is built from two consecutive CLIENT turns — it enshrines the known 98.6% segmentation artifact as correct behaviour

- **File:line**: `Brain/tests/test_ego_trap_transcript_parser.py:105-108`
  (production: `Brain/ego_trap/transcript_parser.py:78-104`)
- **What is wrong**: The fixture is
  `"Anna\nSignal.\n\nAnna\nNo one responded before this next client turn.\n"` — turn 0 and turn 1
  are both CLIENT. `turns_until_next_client(turns, 0)` therefore breaks on the very first
  iteration and returns `[]`, and `classify_response_outcome` returns `"none"` *by construction*,
  not because anybody failed to respond. So the batch DOES cover consecutive client turns —
  and it asserts the defect is the intended semantics. Worse, the sibling test one function
  above (`:93-102`) documents `"none"` in its own docstring as **"the true-silence 'none'"**, so
  the suite explicitly labels the artifact as true silence. CLAUDE.md measures this: of 2,484
  `none` outcomes, **2,449 (98.6%) are immediately followed by another CLIENT turn and 0 are
  genuine silence**. The genuinely-silent case that does exist (35 last-turn-of-call cases) is
  never tested — a test asserting `"none"` when turn 0 is the LAST turn would have been the
  correct fixture and would have made the difference visible.
- **What number it corrupts, and in WHICH DIRECTION**: `"none"` routes to
  `gap_output.write_signal_recognition_failure` (`gap_output.py:200-230`), which calls
  `storage.upsert_signal_recognition_gap(..., recognized=False)` and writes a
  `Signal_Recognition_Failure` gap_event. So the **`signal_recognition_gaps` missed count and
  the `Signal_Recognition_Failure` gap_event count are INFLATED by ~98.6%**, and the CSM
  recognition rate (`recognized / (recognized + missed)`) is correspondingly **DEFLATED**.
  Milestone hit rates are unaffected (only `"csm"` outcomes are scored). This test is precisely
  the mechanism by which the defect survived: the suite is green and asserts the wrong thing.
- **Confidence**: certain
- **Cheapest way to verify**: read `ego_trap/transcript_parser.py:84-89` alongside the fixture
  at `test_ego_trap_transcript_parser.py:106` — the second speaker is `Anna`, the same as the
  first. Then `grep -n 'recognized=False' Brain/ego_trap/gap_output.py`.

#### 2. `test_segmenter.py` pins the `len(sent) < 4` cutoff only from BELOW — it could be raised from 4 to 13 with the whole suite green

- **File:line**: `Brain/tests/test_segmenter.py:4-26` (production: `preprocessing/segmenter.py:23-25`)
- **What is wrong**: The cutoff is constrained on one side only. Measured token counts (spaCy
  `en_core_web_lg`, run locally):

  | fixture | tokens | test |
  | --- | --- | --- |
  | `"K."` | 1 | must be dropped |
  | `"Yeah."` | 2 | must be dropped |
  | `"I mean."` | 3 | must be dropped ← the ONLY thing pinning the floor |
  | multi-idea sentences | 13 / 11 / 16 | `assert len(clauses) >= 2` |
  | normal sentence | 15 | `assert len(clauses) == 1` |

  So a cutoff of `< 4` is required from below (at `< 3`, `"I mean."` survives and the test
  fails), but **any value from 4 up to and including 13 leaves every assertion true** —
  `assert >= 2` on a three-sentence input keeps passing while the 11-token sentence is silently
  discarded. No test asserts that any sentence at or just above the boundary is KEPT.
  In particular `"That makes sense."` is **exactly 4 tokens** — CLAUDE.md names it as the
  de-facto posture filter's boundary case (630 occurrences, the raw material for
  `client_expresses_uncertainty`) — and moving the cutoff 4 → 5 deletes it from the pool with
  the suite still green. Secondary: `test_multi_idea_utterance` asserts `>= 2` where the
  correct answer is 3, so a segmenter that fused two sentences also passes.
- **What number it corrupts, and in WHICH DIRECTION**: `segment_into_clauses` is shared by
  `v2/layer_a.py:68` (Layer A clause pool) and `v2/layer_c.py:77` (Layer C milestone clause
  pool). An unnoticed upward drift of the cutoff **deflates** the clause-pool size (live figure
  73,771 items), **deflates** the measured content-free share (59.1% — short filler goes first),
  and shifts the Layer C milestone pool, i.e. it silently changes both the taxonomy and the
  385–405 milestone baseline. The tests provide no guard above 4.
- **Confidence**: certain (token counts measured, not inferred)
- **Cheapest way to verify**: `python -c "import spacy; n=spacy.load('en_core_web_lg');
  print([(s.text,len(s)) for s in n('That makes sense. Got it.').sents])"` → `4` and `3`.
  Then read `preprocessing/segmenter.py:23`.

#### 3. The production roster path of `preprocessing/transcript_parser.py` has ZERO test coverage — every test in the batch calls `parse_transcript` with `roster=None`

- **File:line**: `Brain/tests/test_transcript_parser.py:15-55` (production:
  `preprocessing/transcript_parser.py:24-66`, caller `v2/pipeline.py:22-25`)
- **What is wrong**: `v2/pipeline.py` **always** passes `roster=load_roster(str(txt_path))`, and
  the sidecars exist for the live corpus (1,945 speaker entries across the `recordings/`
  `*.speakers.json` files). Every one of the six tests calls
  `parse_transcript(txt, JOVEO, NAREN)` with the default `roster=None`, so `load_roster`,
  `_match_roster_entry`, and the entire roster branch of `_classify` (lines 51-59) are
  never executed by any test in the repo — `grep -rn roster tests/` returns nothing. What the
  suite verifies is the *fallback* heuristic that production does not use for this corpus.
  CLAUDE.md independently records the size of this gap: calling `parse_transcript` without the
  roster produced **28,905 CLIENT turns vs the true 23,949** (~20% inflation).
  A concrete latent bug living in that untested branch: line 55 requires `s == name_l` (exact
  string equality with the roster name) before returning `NAREN`, while `_match_roster_entry`
  matches on prefix — so a transcript line reading `"Naren"` against a roster entry
  `"Naren Shankar"` matches the roster, fails the equality, and falls through to
  `SpeakerRole.JOVEO_OTHER` because `is_rep` is true. His responses would then never enter
  `kb_pairs`. I checked: `grep -rlx "Naren" recordings/*.txt` returns 0 files, so this is
  **latent, not currently live** — but nothing in the suite would catch it if a future
  transcript batch shortens the name.
- **What number it corrupts, and in WHICH DIRECTION**: nothing today (the corpus does not
  trigger the latent bug). What is corrupt is the *assurance*: the CLIENT-turn count (23,949),
  the clause-pool size, and every Layer A coverage figure derive from a code path with no test
  at all, and the known failure mode inflates CLIENT turns by ~20%.
- **Confidence**: certain (that the path is untested); the NAREN mis-classification is
  certain as code behaviour, latent as impact.
- **Cheapest way to verify**: `grep -rn "roster" Brain/tests/` → no hits;
  `grep -n "roster" Brain/v2/pipeline.py` → line 24.

#### 4. `test_ranking_does_not_embed_when_the_pool_already_fits` blesses the silent short-circuit that already destroyed one measurement; no test asserts `scenario_similarity` is always present

- **File:line**: `Brain/tests/test_ego_trap_rubric_lookup.py:61-67` (production:
  `ego_trap/rubric_lookup.py:52-56`)
- **What is wrong**: `rank_benchmark_responses` returns `list(responses)` **unranked and with no
  `scenario_similarity` key** when `len(responses) <= limit`. The test asserts exactly that
  (`== responses`, `embed.assert_not_called()`), i.e. it locks in a function with two
  incompatible return shapes and no way for a caller to tell them apart. This is the exact
  bug CLAUDE.md records for `calibration/dry_run_ego_trap.py`: it called the function with
  `limit == len(rows)`, hit this branch, and its chosen-vs-discarded cosine band silently
  measured nothing. The suite reinforces the contract that caused it — there is no test
  asserting the field is present on every returned row, and no test that the short-circuit path
  is distinguishable from the ranked path.
- **What number it corrupts, and in WHICH DIRECTION**: it does not corrupt a number by itself;
  it removes the guard that would stop the corruption recurring. When it did recur, it
  **nulled out** the chosen (p50=0.646) vs discarded (p50=0.575) separation check entirely —
  the check reported "no data" and was read as a passing measurement.
- **Confidence**: likely (the defect is in callers; the test is what makes the ambiguity
  permanent)
- **Cheapest way to verify**: read `ego_trap/rubric_lookup.py:54-56` and note that the early
  return is the only path that omits `row["scenario_similarity"]`.

#### 5. `test_benchmark_reference_caps_at_the_prompt_budget` asserts the implementation against itself — it passes for every value of `_MAX_BENCHMARK_EXAMPLES` from 1 to 5

- **File:line**: `Brain/tests/test_ego_trap_rubric_lookup.py:101-112`
- **What is wrong**: the assertion is
  `len(text.split("\n\n")) == rubric_lookup._MAX_BENCHMARK_EXAMPLES` — the expected value is
  read from the constant under test. With 5 fixture responses: for a cap of 1-4 the ranking
  truncates and both sides move together; for a cap of 5 the `len(responses) <= limit`
  short-circuit returns all 5 and both sides are 5. It only fails for a cap > 5. A test named
  for a cap that cannot detect the cap changing is the canonical "mock returns X, assert X"
  shape.
- **What number it corrupts, and in WHICH DIRECTION**: `_MAX_BENCHMARK_EXAMPLES` controls how
  many of Naren's responses are pasted into the Step 3 grading prompt. CLAUDE.md's own trial
  measured that **removing the benchmark response moved discrimination 1.30 → 1.12 and the
  null 0.130 → 0.150** — so this constant demonstrably moves the weighted score `W` and the
  discrimination ratio. A silent change to it would move both with the suite green; direction
  depends on the change (more examples anchors the grader harder, raising `W(matched)`).
- **Confidence**: certain (about the test's insensitivity); likely (about magnitude)
- **Cheapest way to verify**: mentally set `_MAX_BENCHMARK_EXAMPLES = 4` at
  `ego_trap/rubric_lookup.py:18` and re-trace lines 101-112 — the assertion still holds.

### CLEAN

Stated specifically so the next person does not re-check these.

- **`tests/conftest.py` is clean.** It only does `sys.path.insert(0, os.path.dirname(__file__))`.
  `tests/__init__.py` exists, so pytest's prepend import mode already puts `Brain/` on the path
  (that is how `from preprocessing...` / `from shared...` resolve); the insert adds `tests/`
  itself. I checked the directory listing for a module that would shadow a top-level Brain
  module (`config.py`, `shared`, `preprocessing`, …) — there is none, only `test_*.py`. No
  shadowing (taxonomy 11), no import-order effect on any number.

- **No numbering/base mismatch anywhere in this batch (taxonomy 3).** I traced the index chain
  end to end: `EgoTrapTurn.index = len(turns)` is assigned *after* the empty-utterance skip
  (`ego_trap/transcript_parser.py:57-73`), so `turns[i].index == i` always holds even when
  segments are dropped; `signal_check.py:338` stores `turn.index`; `rubric_lookup.py:93` and
  `turns_until_next_client` slice `turns[start_index + 1:]` on the same 0-based value;
  `gap_output.py:192/222/258/303` persist it unchanged as `signal_turn_index`.
  `test_turn_indices_sequential` (both parser test files) and the `{"turn_index": 0}` fixture in
  `test_response_window_takes_only_csm_turns_before_the_next_client` are consistent with all of
  it. No off-by-one.

- **No fixture drift in either ego_trap test file (taxonomy 4 / fixture shape).**
  `_resp()` in `test_ego_trap_rubric_lookup.py:13-17` produces exactly the four keys
  `storage.get_responses_for_scenario_multilabel` returns (`pair_id`, `response_text`,
  `call_filename`, `is_primary` — `storage.py:342-345`). `EgoTrapTurn(0, "C", EgoTrapRole.CLIENT,
  "...", "c")` at `:133-140` matches the dataclass field order `index, speaker_raw, role, text,
  call_id`. `_scn()` matches `get_scenarios`'s row keys. Enum members are referenced as members,
  not string literals, so the `JOVEO_OTHER` / `OTHER_JOVEO` word-order trap (the two enums use
  **opposite** word order for the same concept: `SpeakerRole.JOVEO_OTHER` vs
  `EgoTrapRole.OTHER_JOVEO`) cannot bite inside these files. I grepped for raw-string
  comparisons repo-wide — the only remaining ones are in
  `calibration/read_gap_reasons.py:166` (correctly using the ego_trap spelling) and comments
  documenting the already-fixed instance.

- **`test_missing_is_coachable_defaults_to_coachable` is a real, correct cross-module
  constraint.** I verified `scenario_pool.is_coachable` (`bool(info.get("is_coachable", True))`)
  against `shared/relative_match.is_sink_flags` (`not scenario_map[k].get("is_coachable", True)`)
  — the defaults genuinely agree, so the test's docstring claim is true, not aspirational.

- **`test_ranking_prefers_the_most_on_topic_response` / `..._can_choose_a_secondary_label_response`
  / `..._does_not_mutate_the_input_rows` are real tests.** They use hand-built vectors, so they
  test the ranking rule rather than the embedder, and the non-mutation test guards a genuine
  cross-scenario score-leak. One limitation worth knowing but not worth a finding: the vectors
  `[[0,1],[1,0],[0.7,0.7]]` are near-unit-norm, so these tests cannot distinguish
  `relative_match.cosine_sims`'s renormalisation from a raw dot product — the ranking is
  scale-invariant either way, so no number moves.

- **`is_rep` vs `@joveo.com` in the roster sidecars is a non-issue at this corpus size.** I
  checked all 1,945 speaker entries: only **3** have `is_rep=True` with a non-joveo email (2
  files, both `"db"` placeholder emails), and **0** have `is_rep=False` with a joveo email. So
  the `entry.get("is_rep")` branch at `preprocessing/transcript_parser.py:57` — the field
  CLAUDE.md warns `ops/derive_joveo_roster.py` deliberately avoids — is currently near-exact.
  Too small to move any reported number; recorded so it is not re-investigated.
