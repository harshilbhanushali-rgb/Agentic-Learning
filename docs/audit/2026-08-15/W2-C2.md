### FINDINGS

#### 1. The published coverage result "64.9% not_called_for matched vs 65.7% unrelated" is a REP-1-ONLY number, and its sign reverses in rep 2 of the same run

- **File:line**: `Brain/calibration/trial_layer_c_arms.py:337-338` and `:423-426`
- **What is wrong**: `_summarise_reps` builds the published per-side dict as
  `matched = dict(reps[0]["matched"], w=_mean(("matched","w")))`. Only `w` is replaced by
  the across-rep mean. Every other field — `attempts`, `counts`, `w_conditional`,
  `not_called_for_rate` — is carried over from **rep 1 alone**. `_report`'s COVERAGE ARMS
  block then prints all three on one line as if they came from the same estimator:
  `not_called_for {m['not_called_for_rate']} | W uncond {m['w']} | W cond {m['w_conditional']}`.
  Textbook taxonomy item 7 (two estimators reported as one number).
- **What number it corrupts, and in WHICH DIRECTION**: the `not_called_for` comparison that
  CLAUDE.md cites as the second, independent failure of "did this moment call for this
  move". Verified in `artifacts/trial_t3_coverage.json`, arm `arm14_unit_axes`:
  rep 1 = matched 0.6486 / unrelated 0.6571 (matched **lower** by 0.8 pt — the published
  claim); rep 2 = matched 0.6689 / unrelated 0.6000 (matched **higher** by 6.9 pt). The
  published direction is an artifact of which replication happened to be stored; the
  2-rep mean is 0.659 vs 0.629, i.e. matched is *higher*, the opposite of what was
  published. The same defect makes `arm143_full`'s printed `w_conditional`
  (matched 0.637 vs unrelated 0.936) a single-rep figure sitting beside a 2-rep `w`.
- **Confidence**: certain (verified in the artifact, both reps are stored under `reps`).
- **Cheapest way to verify**:
  `python -c "import json;p=json.load(open('artifacts/trial_t3_coverage.json'));a=p['arms']['arm14_unit_axes'];print([(r['matched']['not_called_for_rate'],r['unrelated']['not_called_for_rate']) for r in a['reps']])"`

- **File:line**: `Brain/calibration/trial_layer_c_arms.py:278-301` (`score_coverage_arm`),

#### 6. "43 improved / 17 worsened" counts milestones that exist in only ONE arm, with no counter and no warning

- **File:line**: `Brain/calibration/compare_criteria_ab.py:91-110`
- **What is wrong**: the per-milestone query is a `FULL OUTER JOIN`, and the loop computes
  `ow = (oh+0.5*op)/oa if oa else 0.0`. A milestone present only in `public` therefore gets
  `ow = 0.0` and a positive delta, and is counted as **improved**; one present only in the
  baseline is counted as **worsened**. Nothing counts or prints how many of the 249 rows are
  one-sided. `measure_scoring_noise.py` at least prints
  `milestones present in only one run` (`:271-272`) — this script prints nothing.
- **What number it corrupts, and in WHICH DIRECTION**: the 43/17 *shape* statistic, which is
  the entire argument that the rewrite's effect is real rather than noise
  (`measure_scoring_noise.py:274-282` explicitly says "Compare SHAPE, not only rate"). The
  arm with more attempts (`public`, +11.5%) is the arm that touches more milestones, so
  one-sided rows are systematically `public`-only → they land in **`improved`**. Direction:
  **inflates the "improved" count and the net `+4.48`**, i.e. inflates the evidence that the
  rewrite worked.
- **Confidence**: certain for the mechanism; magnitude unverifiable without the DB.
- **Cheapest way to verify**: add `COALESCE(o.attempts,0)=0 OR COALESCE(n.attempts,0)=0` as
  a counted predicate — or just run the existing FULL OUTER JOIN with
  `WHERE o.rubric_id IS NULL OR n.rubric_id IS NULL` and count.

#### 7. The noise floor's `MOVEMENT RATE` denominator includes milestones that were never attempted in one of the two runs

- **File:line**: `Brain/calibration/measure_scoring_noise.py:215-236, 259-272`
- **What is wrong**: `keys = set(a_side) | set(b_side)`, and `recs` is built over that union
  with `empty = {"a":0,...}` filling the missing side. `moved` is then
  `[r for r in recs if r["delta"] != 0]` and the headline is `len(moved)/len(recs)`
  labelled `<-- THIS IS THE FLOOR`. A milestone attempted only in run B contributes
  `delta = W_B - 0`: it enters the denominator always, and the numerator whenever `W_B > 0`.
  Those are coverage differences, not scoring variance. The script *computes*
  `only_one_side` (`:229`) and prints its count (`:271-272`) but never excludes it, and
  never reports the movement rate on the intersection.
- **What number it corrupts, and in WHICH DIRECTION**: the "15.6% (37/237)" floor, the
  "|delta| median/max" line, and — worst — the `24 up / 13 down, net +2.12` shape used to
  argue the criteria rewrite's lopsidedness is signal. One-sided rows are signed by which
  arm has them, so they contribute a **systematic** up/down skew rather than variance.
  CLAUDE.md explains the floor's lopsidedness as "at a ~3% hit rate a random flip can only
  move UP"; part of it is more likely just B-only milestones. The rate itself moves in an
  ambiguous direction (zero-W one-sided rows dilute it downward, non-zero ones push it up),
  which is exactly why it should not be quoted as "the floor" without the intersection
  figure beside it.
- **Confidence**: certain for the mechanism; the sign of the net effect on the *rate* is
  data-dependent and I could not measure it (no saved log of this comparison exists in
  `Brain/logs/`).
- **Cheapest way to verify**: re-run with the same schemas and read the existing
  `milestones present in only one run: N` line — if N is a meaningful fraction of 237, the
  floor as published is not a floor.

### MINOR — real but small

- **`gate()` passes when the null is exactly zero.**
  `trial_layer_c_arms.py:353-359`: `passes = w_m > 0 and w_u < 0.5*w_m`, `ratio = inf` when
  `w_u == 0`. There is no minimum-attempts guard, so a tiny run trivially passes the
  headline gate — `artifacts/trial_smoke.json` has `arm0_baseline` at ratio `inf`,
  `passes: True` on 16 attempts. Taxonomy item 5.
- **`trial_layer_c_arms` collects model provenance and throws it away.**
  `:706-715` — every call site is `m_rec, _ = score_milestone_arm(...)`; the `models`
  Counter is discarded and never reaches `payload` or `_report`. The ceiling harness records
  and prints exactly this (and the artifact shows why it matters — finding 3). Per-record
  `scored_by` survives, but only for rep 1: `_summarise_reps` keeps
  `"records": reps[0]["records"]` and strips `records` from every other rep, so half of each
  arm's paid verdicts are not persisted at all.
- **`compare_criteria_ab.py:82-83` prints an unsigned drift with a `+` format.**
  `drift = abs(a[0]-b[0])/b[0]` then `f"({drift:+.1%})"` — a *drop* in attempts prints as
  `+x%`. It happened to be correct for the published run (864 → 963) but the displayed
  sign is not derived from the data.
- **`stratified_sample`'s overshoot trim is alphabetical, not random.**
  `trial_layer_c_arms.py:149-150`: `chosen.discard(sorted(chosen)[-1])`. Rounding can
  overshoot by 1-2, and the correction always removes the alphabetically-last key — a
  deterministic, non-random exclusion inside a function whose docstring promises a seeded
  sample. Effect is bounded at 1-2 scenarios.

### CLEAN

Things I checked specifically and found correct — stated so nobody re-checks them:

- **`compare_criteria_ab.py`'s `(rubric_id, milestone_id, csm_id)` join is sound *for the
  run it was written for*, and the risk is real but not realised here.** `upsert_rubric`'s
  `ON CONFLICT (scenario_id)` does keep `rubric_id` stable while replacing `milestones`, so
  `M2` can change meaning across a Layer C re-run. But the arm under comparison was produced
  by `ops/rewrite_milestone_criteria.py`, which rewrites descriptions **in place** over the
  same array (CLAUDE.md records "0 rubrics changed milestone count, all 391 `support_calls`
  preserved byte-for-byte"), so positions did not move. **What is missing is the guard, not
  the correctness**: the script's only precondition test is attempt-count drift, which
  cannot detect milestone-identity drift at all — a re-pointed `M2` produces a perfectly
  plausible number. A one-line check comparing `support_calls`/`support_clauses` per
  `(rubric_id, position)` across the two schemas would close it. I did not raise this as a
  finding because I could find no evidence the identity actually drifted.
- **Taxonomy item 3 (numbering/base mismatch): correct everywhere in these four files.**
  `milestone_ids` produces `f"M{i+1}"` from the array position, `v2/layer_c` writes
  `order = i+1` over the same list, `describe_items_for` uses `order_idx + 1`, and the
  ceiling's `aggregate`/`counters` round-trip `f"{rubric_id}::{milestone_id}"` and split it
  back without collision (milestone ids never contain `::`).
- **Taxonomy item 4 (name that never matches): no dead literals.** `_ARMS`, `ARMS`,
  `arm_units`, `_NO_BENCHMARK_ARMS`, `_LEGACY_REGEN_ARM` all agree; `--arms` validates
  against `ARMS` and raises on an unknown name; `_VALID_VERDICTS` /
  `coverage_areas.VALID_VERDICTS` match what the prompts enumerate; the counter keys read
  by `arm_totals` (`"full_hit"`, `"partial_hit"`) match `_normalize_verdict`'s vocabulary.
- **Taxonomy item 9 (silent short-circuit) is explicitly handled in the ceiling.**
  `_verify_ranking_equivalence` (`:339-364`) knows about
  `rank_benchmark_responses`'s `<= limit` early return and compares sets rather than order
  in that case — the one place this repo previously got burned. It runs before any Gemma
  spend and aborts on mismatch.
- **The zero-write enforcement is real, in both harnesses that touch the DB for scoring.**
  `_connect_read_only` issues `SET SESSION default_transaction_read_only = on` and
  *verifies the setting took* before returning; `trial_layer_c_arms` reuses it.
  `ego_trap.gap_output` and `shared.checkpoint` are genuinely never imported by either file
  (grep confirms).
- **`take_sample` is honest random, not similarity-ranked** (`:145-153`), and
  `a3_eligible` / `hold_out` filter on `call_id` / `call_filename` rather than `pair_id`,
  which is the stricter and correct choice for both leaks. The A3 stratum construction is
  the one part of the ceiling I found no defect in.
- **`trial_layer_c_arms`'s matched/unrelated populations are drawn from the SAME rows** —
  `_items(arm_rubrics[arm], lambda k: k)` vs `_items(arm_rubrics[arm], lambda k: partner[k])`
  iterate the identical `samples` dict, and both draw from the leakage-clean
  `a3_eligible` stratum. This is the symmetry the ceiling lacked, and it is correct here
  apart from the skipped-partner drop in finding 8.
- **`--limit` vs `--sample` defaults are safe.** Both default to `0`, which means "all
  scenarios"; `--limit` prints a loud non-representativeness warning at `:528-531`, passing
  both raises, and `_report` shouts when a sample contains zero posture scenarios. Taxonomy
  item 13 is properly defended *in this file* — the residual alphabetical selector is in
  `score_naren_ceiling.py`'s `--max-items-per-arm` (finding 12).
- **`measure_scoring_noise.py`'s `--dedup` path is sound.** `_assert_faithful` proves the
  `gap_events` rebuild reproduces the stored counters on the *same* schema before any
  deduplicated number is reported, and refuses otherwise; `DISTINCT ON ... ORDER BY ...,
  gap_event_id` deterministically keeps the earliest verdict per signal. The duplicate-run
  precondition itself is the right check, correctly keyed on
  `(call_id, scenario_key, signal_turn_index)`.
- **Taxonomy item 14 (correlated observations): no significance test is computed in any of
  these four files**, so there is no false-independence claim to find. The ceiling and the
  trial report point estimates and (in the trial) a replication range; neither computes a
  p-value, a CI, or a bootstrap. Whether the *published prose* over-reads those point
  estimates is finding 11, not a statistics bug.
